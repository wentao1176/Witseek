## 四、本阶段逮到的真实缺陷

### 1. 文件树把深路径的源码整段截掉（`MAX_DEPTH = 6`）

**表现**：左栏 `xwt` 目录画着展开箭头（▾）却没有子项。而磁盘上
`app/src/main/java/com/xwt/schedule/` 下确实有两个 `.java` 文件。

**根因**：`workspace.ts` 的 `MAX_DEPTH = 6`。数一下层级：

```
app                                 depth 0
app/src                             depth 1
app/src/main                        depth 2
app/src/main/java                   depth 3
app/src/main/java/com               depth 4
app/src/main/java/com/xwt           depth 5
app/src/main/java/com/xwt/schedule  depth 6   ← 被 walk 的 depth>=maxDepth 挡在门外
```

`walk()` 在 `depth >= maxDepth` 时直接返回，所以 `schedule` 及其下所有文件**根本没进树**。
而 `xwt` 是目录，渲染侧照样给它画展开箭头 —— 于是呈现为"展开了却空的目录"。

**这不是演示环境的特例**：用户本机 `D:\class_table` 的源码路径
`app/src/main/java/com/xwt/schedule/…` 深度完全一样，也就是说**真实项目里这棵树会藏起全部源码**。

**修法**：`MAX_DEPTH` 6 → 12。真正兜底的是 `MAX_ENTRIES = 4000`（深度大但目录浅，条目数不会因此失控）。

### 2. 连带发现：深路径下文件名被省略号吃掉

`MAX_DEPTH` 放宽后，深度 7 的行缩进 = `8 + 7 × 14 = 106px`，而侧边栏固定 236px，
文件名只剩约 76px —— `HolidayUtils.java` 显示成 `HolidayU...`。
**最先被截掉的恰恰是这棵树里唯一有用的信息**。

**修法**：缩进 14px → 10px/层；侧边栏 236px → 288px（中间对话区仍有 852px，不受挤压）。
修复后 `HolidayUtils.java`、`MainActivity.java`、`activity_main.xml` 全部完整显示。

### 3. 白屏：运行中的 Electron 是旧构建

**表现**：窗口标题正常显示 `Witseek`，内容**全白**。

**根因**：`dev.sh` 在 18:09 启动，主进程 / preload 只在那一刻构建过一次。18:28 脚手架覆盖了
`src/main/*.ts` 与 `src/preload/index.ts`，但 **electron-vite 只对渲染进程做了 HMR，主进程与
preload 从未重建**。于是运行中的 Electron 仍是 P1 版本：preload 只暴露 `platform` / `getAppInfo`，
而 P3 渲染进程要调 `window.witseek.getAutoPrompt()` —— 一调就 `TypeError`，React 挂载失败，白屏。

**判别方法**（比看界面可靠）：直接量构建产物。

```
修复前： out/main/index.mjs    2.39 kB   （2 modules transformed）
        out/preload/index.mjs  0.25 kB
修复后： out/main/index.mjs   60.93 kB   （25 modules transformed）
        out/preload/index.mjs  2.44 kB   （3 modules transformed）
```

**修法**：改完主进程 / preload 后必须重启 dev 进程，不能指望 HMR。

### 4. 上一轮实例没死干净，和新实例抢同一份日志

**表现**：日志里混着 `[ELIFECYCLE] Command failed.` 与上一个实例的
`GPU process isn't usable. Goodbye.`，看起来像新实例启动失败，实际是残骸在写同一个文件。

**根因**：`dev.sh --stop` 只按 pidfile 杀进程组，`setsid` 出去的 Electron 子进程会漏掉。
更麻烦的是我自己在清理时写的 `pkill -f "electron-vite"` —— **模式串就出现在执行它的那个 shell
的命令行里，pkill 把调用者一起杀了**，表现为 SSH 命令输出为空。这个坑 DESIGN.md §10 里 P1 阶段
已记录过一次，这次又踩了同一个。

**修法**：`dev.sh --stop` 增加兜底扫描，模式以 `[e]` 起头规避自伤：

```bash
if pkill -f '[e]lectron-vite' 2>/dev/null; then stopped=1; fi
if pkill -f '[e]lectron/dist' 2>/dev/null; then stopped=1; fi
```

### 5. 测试夹具自身写错（1 例）

`defaultCollapsed` 的用例里，我只塞了 `app/src/p0/Main.java` 这样的**文件**条目，
没塞对应的目录条目，于是折叠集合自然为空，断言 `folded.has('app/src/p0')` 失败。
实现是对的，夹具是错的 —— 顺手把「文件永远不进折叠集合」这条也改成有目录参与的真实场景。

### 在虚拟显示上点按钮

无头环境没有可交互的桌面，但 `xdotool` 可以在 `:100` 上合成真实鼠标事件。
关键是**不要目测坐标** —— 截图经过缩放，目测误差能到上百像素。做法是程序化定位：

```bash
export DISPLAY=:100
XD=$PWD/.tools/xdotool/prefix/usr/bin/xdotool
export LD_LIBRARY_PATH=$PWD/.tools/xdotool/prefix/usr/lib/x86_64-linux-gnu
$XD mousemove 579 858 && $XD click 1
```

坐标来源：读 `xwd -root` 的原始像素，先按颜色找出审批卡（琥珀底 `rgb(250,238,218)`）的行范围，
再在卡片内部找主按钮的填充色（`rgb(230,241,251)`），取该色块的几何中心。
`xdotool` 经 `bash scripts/fetch_deb_tree.sh .tools/xdotool xdotool` 用户态解包安装。
